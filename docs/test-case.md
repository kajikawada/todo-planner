# To-do Planner — Test Cases

Status: Draft v1 · Last updated: 2026-09-27 · Based on: `docs/spec.md` Draft v1

This document lists every test the To-do Planner must pass before a change is considered done. The app is generated by AI, so the tests are written to be **precise, deterministic, and traceable to the spec**. A person or an agent should be able to run them without guessing.

- `docs/spec.md` is still the source of truth. If a test here disagrees with the spec, the spec wins, and this file must be fixed in the same change.
- §2 lists the gaps in the spec and the **assumption each test makes**. Settle each one by updating the spec, then remove it from §2.

---

## 1. Conventions

### 1.1 Test IDs and levels

| Prefix  | Level                  | Target                                   | How it runs                       |
|---------|------------------------|------------------------------------------|-----------------------------------|
| `DT-`   | Unit                   | `js/utils/date.js`                       | `node --test tests/` (automated)  |
| `MC-` `MV-` `MQ-` `MF-` `MS-` `MG-` `MD-` | Unit | `js/model.js`            | `node --test tests/` (automated)  |
| `ST-`   | Unit                   | reducer in `js/store.js`                 | `node --test tests/` (automated)  |
| `SG-`   | Unit                   | `js/storage.js` (mock `localStorage`)    | `node --test tests/` (automated)  |
| `AR-`   | Static conformance     | source files under `js/`                 | `node --test tests/` (automated)  |
| `E-*-`  | End-to-end (UI)        | the app in a real browser                | by hand or by a browser agent     |

**Priority:** **P1** blocks release · **P2** must pass before the feature is "done" · **P3** nice to verify.

### 1.2 Test file mapping

| Test file                        | IDs                          |
|----------------------------------|------------------------------|
| `tests/date.test.js`             | `DT-*`                       |
| `tests/model.test.js`            | `MC-* MV-* MQ-* MF-* MS-* MG-* MD-*` |
| `tests/store.test.js`            | `ST-*`                       |
| `tests/storage.test.js`          | `SG-*`                       |
| `tests/conformance.test.js`      | `AR-*`                       |

Put the test ID in each test name, e.g. `test('MQ-03 tag in the middle is removed from the title', …)`, so failures trace back to this file.

### 1.3 Unit-test rules

- Use only `node:test` and `node:assert/strict`. No test dependencies (CLAUDE.md).
- Never read the real clock in a test. Pass `today` (a `YYYY-MM-DD` string) and `now` (an ISO string) explicitly. Use `mock.timers` from `node:test` for debounce tests.
- Freeze inputs (`Object.freeze`, deeply) in every model and reducer test, so any in-place mutation throws.
- Run the date and model suites under several time zones. They must pass in all of them:
  ```sh
  for tz in UTC America/Los_Angeles Asia/Tokyo Pacific/Kiritimati Pacific/Pago_Pago America/New_York America/Santiago; do
    TZ=$tz node --test tests/ || echo "FAILED in $tz"
  done
  ```
  `Pacific/Kiritimati` (UTC+14) and `Pacific/Pago_Pago` (UTC−11) catch UTC-vs-local bugs. `America/New_York` catches DST bugs. `America/Santiago` has DST changes at midnight, so some local days have no 00:00.

### 1.4 Reference dates

Unless a test says otherwise, **T = `2026-09-27` (a Sunday)**. `T-2` means two days before T, and so on.

### 1.5 Assumed function contracts

The spec names the model functions but not their signatures. The tests assume the contracts below. If the implementation chooses others, update this table and the tests together.

| Function | Assumed contract |
|---|---|
| `createTask(fields, { id, now })` | Returns a new Task with defaults applied. `now` is an ISO string used for `createdAt` and `updatedAt`. `id` is injected so the function stays pure. |
| `validateTask(task, categories)` | Returns `{ valid: boolean, errors: { [field]: string } }`. |
| `parseQuickAdd(text)` | Returns `{ title: string, tags: string[] }`. Doesn't validate. |
| `normalizeTags(input)` | Takes a comma-separated string or an array. Returns trimmed, lowercased, unique tags, empty ones dropped, in first-seen order. |
| `filterTasks(tasks, filters)` | `filters = { status: 'active'\|'completed'\|'all', category: string\|null, tags: string[], day: string\|null, search: string }`. |
| `sortTasks(tasks, sortKey)` | `sortKey` is `'default'`, `'priority'`, or `'created'`. Returns a new array. |
| `groupTasks(tasks, today)` | Returns `[{ key, label, tasks }]` in the order overdue, today, upcoming, nodate, completed. Empty groups are left out. |
| `dueStatus(task, today)` | Returns `'overdue'`, `'today'`, `'upcoming'`, `'none'`, or `'completed'`. |
| `countByCategory(tasks, categories)` / `countByTag(tasks)` | Return counts of **active** tasks. |
| date helpers | `toISODate(Date)`, `parseISODate(str)` → local-midnight `Date` or `null`, `isValidISODate(str)`, `compareDates(a, b)`, `addDays(str, n)`, `diffDays(a, b)`, `relativeLabel(due, today)`, `formatShort(str)`, `monthGrid(year, monthIndex0, weekStart)`. |
| reducer | `reduce(state, action)` is exported from `store.js` as a pure function, so it can be unit-tested. |
| storage | `load(backend)`, `save(state, backend)`, `createSaver(backend, delayMs)`, `migrate(data)`. `backend` is an object with the `Storage` interface and defaults to `localStorage`. |

## 2. Spec gaps and assumptions

Each item below is not settled by the spec. The tests take the stated assumption. **Resolve each one in `docs/spec.md`** and then update or delete the item.

| ID | Gap | Assumption used by the tests |
|----|-----|------------------------------|
| A-01 | How title length is counted. | Length is `title.trim().length` (UTF-16 code units). |
| A-02 | Whether `#tag` text is removed from the quick-add title. | Yes. `Buy milk #errand` → title `Buy milk`. Whitespace left by removing a tag collapses to one space. |
| A-03 | What counts as a `#tag` in quick-add. | `#` at the start or after whitespace, followed by one or more chars up to whitespace or a comma. `C#` and a lone `#` are plain text. |
| A-04 | Quick-add tag longer than 30 chars. | It is not a tag; the text stays in the title as typed. |
| A-05 | Tags with inner spaces in the edit dialog (`to do`). | Invalid; show an inline error. |
| A-06 | Relative label for an upcoming date in another year. | Same `MMM D` format with no year (`Jan 8`). |
| A-07 | Label text for an overdue date. | Short date plus the "Overdue" label (`Sep 25` · Overdue). |
| A-08 | Whether sidebar tag counts include completed tasks, and whether a tag used only by completed tasks is listed. | Counts include active tasks only. Tags used only by completed tasks are still listed, with count 0. |
| A-09 | Order of tags in the sidebar. | Alphabetical. |
| A-10 | "Sort by priority" tie-breakers. | Incomplete first → priority high→low → due date asc (no date last) → `createdAt` asc. |
| A-11 | "Sort by creation date" direction. | Incomplete first → `createdAt` **descending** (newest first). |
| A-12 | Order of completed tasks in the default sort. | The same keys as for incomplete tasks (§3.3 applied literally). |
| A-13 | Full ties (equal on every key). | The sort is stable; the input order is kept. |
| A-14 | Search text with surrounding whitespace. | It is trimmed. Whitespace-only search means "no search filter". |
| A-15 | Whether the calendar day filter applies in the List view and shows as a chip. | Yes. Selecting a day adds a removable "day" chip, and the filter applies in both views. |
| A-16 | Quick-add inheritance when several tag filters are active. | The new task gets all of them. |
| A-17 | Deleting a second task while the first Undo toast is visible. | The first deletion becomes final. The toast now offers Undo for the second task only. |
| A-18 | Stored `version` higher than the app supports. | Treated as corrupt: back it up, start empty, show the warning. |
| A-19 | One invalid task inside otherwise valid stored data. | The whole payload is treated as corrupt (backup, empty state, warning). |
| A-20 | Initial categories on first run. | `["Work", "Personal"]`, as in the spec example. |
| A-21 | Month grid size. | The fewest full weeks that cover the month (4, 5, or 6 rows). |
| A-22 | Whether sort, filters, and week-start survive a reload. | Filters and search reset (status back to Active). View, visible month, sort, and week-start are saved under `todo-planner:ui`. |
| A-23 | Arrow keys at the edge of the month in the calendar. | Focus moves into the adjacent month and the grid changes month. |
| A-24 | Category names compared when a task is validated. | Exact, case-sensitive match against the `categories` list. |
| A-25 | Mockup in spec §4 labels Sep 27 as "Sat". 2026-09-27 is a **Sunday**. | Tests use the real weekday. Fix the mockup. |
| A-26 | Punctuation right after a quick-add tag (`Call #mom, today`). | Open. The tag ends at the comma; the spec must say what the title becomes (`Call, today` is suggested). |

### 3.1 Unit-test task builder

Use one helper in the tests so each case states only the fields it cares about:

```js
const BASE_NOW = '2026-09-27T09:00:00.000Z';
export function task(overrides = {}) {
  return Object.freeze({
    id: overrides.id ?? '00000000-0000-4000-8000-000000000001',
    title: 'Task',
    notes: '',
    dueDate: null,
    priority: 'medium',
    category: null,
    tags: Object.freeze([]),
    completed: false,
    createdAt: BASE_NOW,
    updatedAt: BASE_NOW,
    completedAt: null,
    ...overrides,
  });
}
```

### 3.2 End-to-end seed data (S1–S10)

Most `E-` tests start from this seed. It is relative to the tester's real today (T). Run it in the DevTools console on the app page, then the page reloads:

```js
(() => {
  const pad = (n) => String(n).padStart(2, '0');
  const d = (off) => {
    const x = new Date();
    x.setHours(12, 0, 0, 0);
    x.setDate(x.getDate() + off);
    return `${x.getFullYear()}-${pad(x.getMonth() + 1)}-${pad(x.getDate())}`;
  };
  const base = Date.parse('2026-01-01T00:00:00Z');
  const t = (i, title, due, priority, category, tags, extra = {}) => {
    const ts = new Date(base + i * 60000).toISOString();
    return {
      id: `00000000-0000-4000-8000-${String(i).padStart(12, '0')}`,
      title, notes: '', dueDate: due, priority, category, tags,
      completed: false, createdAt: ts, updatedAt: ts, completedAt: null, ...extra,

    t(2, 'Team standup notes', d(0), 'medium', 'Work', []),
    t(3, 'Book dentist', d(1), 'low', 'Personal', []),

    t(5, 'Renew passport', d(10), 'high', null, ['travel']),
    t(6, 'Read book', null, 'low', 'Personal', []),
    t(7, 'Pay rent', d(-5), 'high', 'Personal', ['billing'],
      { completed: true, completedAt: '2026-01-02T00:00:00.000Z' }),
    t(8, 'Buy milk', null, 'medium', null, ['errand'], { notes: '2 liters, organic' }),
    t(9, 'Fix bug', d(0), 'high', 'Work', ['urgent']),
    t(10, 'Water plants', d(0), 'medium', null, []),
  ];
  localStorage.setItem('todo-planner:v1',
    JSON.stringify({ version: 1, tasks, categories: ['Work', 'Personal'] }));
  localStorage.removeItem('todo-planner:ui');
```

## 11. How to run a full test pass

1. Run the unit and conformance tests in every time zone (§1.3). All must pass.
2. Serve the app (`python3 -m http.server 8000`), open DevTools with the console visible.
3. Load the seed (§3.2) before each `E-` section, or empty storage where a test says "Empty start".
4. Run every P1 `E-` test in each row of the matrix (§3.3), and every P2 `E-` test in row 1.
5. Record the result for each ID (pass/fail, browser row, note). Any P1 failure blocks the change.
6. If a test exposed a spec gap, add it to §2 and fix the spec, not only the code.
